> ⚠️ 状态:AI 起草,未经人工审核——不得直接作为结论依据

## 机理

链路利用率长期逼近带宽上限时,队列排队时延与缓存丢包急剧上升,新业务时延抖动、重传增多。抓包文件按秒分桶统计每秒总字节数,可判断「这一段时间里链路是否被打满」,这是趋势性风险而非单点故障。

## 判断标准

当前 P13 使用固定门槛：连续 ≥10 秒每秒字节数 ≥12,500,000（约 100 Mbps）。它只提示该抓包点出现高流量，不能在未知链路额定速率和镜像范围时断定“饱和”；例如 1 Gbps 链路上的 100 Mbps 可能并未接近容量。

## 报文证据特征

- 用 IO 统计直接核对:`tshark -r <文件>.pcap -q -z io,stat,1`,查看每秒 Bytes 列是否连续贴着链路带宽。
- 饱和伴随特征:`tcp.analysis.retransmission` 增多、`tcp.analysis.window_full` 增多、RTT(`tcp.analysis.ack_rtt`)整体抬升。
- 若字节数贴线但无重传,可能是抓包点所在链路本身带宽即如此,需换点复测。

## 排查步骤

1. 每秒字节数总览:`tshark -r <文件>.pcap -q -z io,stat,1`,与链路带宽(如 1Gbps=125,000,000 B/s)对比。
2. 找出占带宽最大的会话:`tshark -r <文件>.pcap -q -z conv,tcp` 与 `-z conv,udp`,按 Bytes 排序。
3. 找出占带宽最大的主机:`tshark -r <文件>.pcap -q -z endpoints,ip`。
4. 按分钟看趋势:`tshark -r <文件>.pcap -q -z io,stat,60`(注意对照业务时段)。

## 处置建议

确认峰值时段与来源后:非关键大流量(备份、补丁分发)错峰或限速;QoS 保障会议/办公关键应用;扩容上联链路。持续命中本规则说明需要容量规划,建议将抓包时间窗覆盖典型业务峰谷再下结论。
